# 将棋バリアント対戦サイト 初期仕様書

## 1. 概要

普通の将棋ルールから駒落ち戦、獅子王、取る一手将棋、自由な初期盤面、特殊サイズ盤面（5×5, 3×3等）、将棋vs囲碁といった様々なバリアントルールを選んで対戦できるWebサイト。CPU戦・プライベートマッチ・カジュアルマッチに対応し、過疎対策として「一定の範囲からランダムなルールでオンラインマッチング」するモードを持つ。将来的にはある程度強いAIも育てていく。

## 2. アーキテクチャ概要

```
[Next.js (フロント)] --HTTP--> [Express API] --Prisma--> [MySQL]
        |                          |
        |--WebSocket(Socket.io)--> [対局サーバー(Node.js)]
                                        |
                                   [Redis] ← マッチング待機列 / 対局中の一時状態
```

- **フロント**: Next.js（App Router）。盤面はSVG/Canvasで自作コンポーネント。ロビー・マッチング・対局画面すべてReactコンポーネントで統一。
- **リアルタイム通信**: Socket.ioで対局同期（着手・王手・投了・切断復帰）。
- **永続化**: MySQL + Prisma（ユーザー、ルールセット、対局結果、レーティング）。
- **一時状態**: 対局中の盤面はメモリ + Redis（サーバー再起動耐性・マルチプロセス対応用）。終局時にMySQLへ確定保存。
- **AI**: 別プロセス/ワーカーとして分離し、対局サーバーと疎結合にする（後で強化しやすくするため）。

## 3. ルールエンジンの汎用化設計（最重要部分）

将棋の「標準ルール」をハードコードせず、以下をパラメータ化した`RuleSet`として表現する。

```ts
type RuleSet = {
  boardWidth: number;        // 3,5,9...
  boardHeight: number;
  pieceSet: PieceDefinition[]; // 駒種と動き(獅子の二段階移動なども個別定義)
  initialSetup: {
    sente: PlacementRule;    // 駒落ち・自由配置に対応
    gote: PlacementRule;     // 相互駒落ちにも対応(左右非対称OK)
  };
  captureRule: {
    mandatoryCapture: boolean;      // 取る一手将棋
    ignoreIfLeavesKingInCheck: boolean; // 王手放置になるなら免除
  };
  dropRule: 'standard' | 'none' | 'custom'; // 持ち駒使用可否
  drawConditions: DrawRuleConfig; // 千日手/持将棋(27点法等)/入玉ルールなど選択式
  crossGameMode?: 'shogi-vs-go' | null; // 特殊モード
};
```

- **駒の動き定義**: 通常駒は「方向×距離(無限/1マス)」テーブルで表現。獅子のような「1ターンに2回移動でき、2枚連続で取れる」駒は`specialMove: 'double-step'`のような拡張フラグで個別実装（汎用テーブルでは表現しきれないため）。
- **合法手生成**: 汎用ジェネレータが`RuleSet`を受け取り、盤サイズ・駒定義・特殊ルールに応じて合法手を計算。取る一手ルールはフィルタ層として追加適用。
- こうすることで「3×3ミニ将棋」も「9×9標準」も「相互駒落ち」も同じエンジンで扱え、新ルール追加時もコード全体を触らずに済む。

## 4. 初期実装候補ルールと法的リスクの整理

| ルール | 実現方法 | 注意点 |
|---|---|---|
| 通常将棋 | 標準RuleSet | 問題なし（将棋のルール自体に著作権なし） |
| 駒落ち(通常/相互) | initialSetupの非対称配置 | 問題なし |
| 獅子（獅子王） | 中将棋由来の伝統駒、動き拡張 | 中将棋は伝統ゲームでパブリックドメイン。問題なし |
| 取る一手将棋 | mandatoryCapture:true | 問題なし（伝統的なローカルルール名） |
| 自由な初期盤面 | initialSetup:custom | 問題なし |
| 5×5, 3×3等 | boardサイズ変更 | 「どうぶつしょうぎ」等の**商標登録された特定商品の盤面・駒デザインをそのまま模倣するのはNG**。サイズ縮小自体は問題ないが、既存商品名やデザインの流用は避ける |
| 持将棋/引分けルール | drawConditions選択式 | 問題なし（27点法など公知ルール） |
| 将棋vs囲碁 | 別モジュール(混成ルール) | 独自ルールなので著作権問題なし。ただしゲームバランス設計が難しく優先度は低めに |

→ 「どうぶつしょうぎ」的な可愛い動物駒バリアントを作りたくなっても、既存商品のデザイン・駒名を模倣しないことだけ徹底すれば法的リスクは低い。

## 5. マッチング設計

- **CPU戦**: 難易度選択（AIロードマップに連動）
- **プライベートマッチ**: ルームコード発行、ルールセットをホストが選択
- **カジュアルマッチ**: レーティングなし、即マッチ
- **ランダムルールオンラインマッチング**（過疎対策の目玉機能）:
  - ユーザーは「許容できるルール範囲」をタグで選択（例: 盤サイズ、駒落ちあり/なし、特殊駒あり/なし）
  - マッチング待機列で条件の積集合があるユーザー同士を優先マッチ
  - 一定時間マッチしなければ条件を段階的に緩和（緩和幅も設定可能）
  - Redisのソート済みセット等で待機列管理

## 6. AI設計ロードマップ

1. **Phase1**: Minimax + αβ枝刈り + 単純な駒得評価関数（小盤面なら十分強い）
2. **Phase2**: 標準9×9向けに評価関数を拡張（駒の効き・玉の安全度など手作りパラメータ）
3. **Phase3（将来）**: 自己対戦による評価関数の強化学習/NNUE的アプローチ

RuleSetパラメータ化のおかげで、Minimaxの合法手生成は変則ルールでもそのまま使い回せる（評価関数だけ変則駒用に多少の調整が必要）。

## 7. DB設計（Prisma概要）

```prisma
model User { id, name, email, rating, createdAt, ... }
model RuleSet { id, name, config Json, isPublic, createdBy, category }
model Game {
  id, ruleSetId, senteUserId, goteUserId, mode // cpu/private/casual/randomMatch
  status, result, startedAt, endedAt
}
model GameMove { id, gameId, moveNumber, from, to, piece, capturedPiece, timestamp }
model MatchQueueEntry { userId, acceptedRuleTags Json, enteredAt } // Redis管理でも可
```

## 8. 決定事項

- **フロントエンド**: Next.js（App Router）+ 盤面はSVG/Canvas自作コンポーネント（Phaserは不採用）
- **MVP範囲**: 標準9×9将棋のみ先行リリース（CPU戦 + プライベートマッチ）。ルールエンジンは最初から汎用パラメータ設計にしておき、Phase2以降で駒落ち・盤サイズ変更・取る一手ルールを追加投入

## 9. フェーズ計画

| Phase | 内容 |
|---|---|
| **0** | プロジェクト初期化（Next.js + Express + Prisma + MySQL構成、Socket.io疎通確認） |

| **4** | 獅子（獅子王）・持将棋/引分けバリエーション拡充・将棋vs囲碁・AI強化 |
