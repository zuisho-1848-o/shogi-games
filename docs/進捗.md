### 構成方針

- npm workspaces によるモノレポ:
  - `packages/rule-engine` … 将棋ルールエンジン(純粋TSロジック、フレームワーク非依存)。ここを汎用パラメータ化しておくのが最重要
  - `packages/db` … Prismaスキーマ + クライアント
  - `apps/server` … Express + Socket.io（対局サーバー、REST API）
  - `apps/web` … Next.js（フロント）
- 理由: rule-engineをパッケージ分離しておくと、将来AIワーカーやテストからも同じロジックを再利用でき、フロント/サーバーどちらからもimportできる。

### rule-engine 実装メモ

- 内部座標は `row`(0=盤面上端=後手最奥) / `col`(0=盤面右端) に統一。駒の動きは先手基準(前進=-row)で定義し、後手は`toBoardDirection`で反転させる方式にした。汎用RuleSetでも同じテーブルを使い回せる。
- 標準駒13種（歩香桂銀金角飛王+成り駒5種）を実装。合法手生成は「疑似合法手生成→自玉が王手に晒される手を除外」という素直な方式（盤面が小さい前提なので毎回全駒の利きを再計算しても十分速い）。
- **MVPでは省略した実装**（Phase2以降で必要になったら追加）:
  - 二歩は実装済みだが、**打ち歩詰め(うちふづめ)は未実装**。打ち歩による詰みも合法として扱ってしまう。
  - **千日手(同一局面の繰り返し)判定は未実装**。`drawConditions.sennichite`フラグは型として用意済みだが未接続。
  - 持将棋(27点法)も型のみ用意で未接続。
  - 手番側の合法手が0の場合は一律「手番側の負け」としている。本来は王手されていない場合の着手不能はまず起こらないはずだが、変則ルール(盤サイズ極小・自由配置など)では起こりうるので、その際の扱い(引き分け等)は要検討。
- `captureRule.mandatoryCapture`(取る一手将棋)は合法手生成のフィルタとして実装済み。標準RuleSetでは`false`にしてあるので今は無効。
- 動作確認: 標準将棋の初期局面で先手の合法手が30通りであることを確認済み（既知の値と一致）。

### DB (packages/db)

- Prismaスキーマ: `User` / `RuleSetPreset`(RuleSetをJsonでまるごと保存) / `Game` / `GameMove`。
- ローカル開発用にMac標準の`/usr/local/mysql`(8.4)がすでに起動していたのでそれを利用。`shogi_games_dev`というDBを作成し、`packages/db/.env`に`DATABASE_URL="mysql://root@localhost:3306/shogi_games_dev"`を設定してmigrate済み（ユーザー環境固有の設定。本番/他マシンでは要変更）。
- `MatchQueueEntry`(マッチング待機列)はPhase3で作る予定だが、待機列は揮発性が高くRedis向きなのでDBモデルとしては作らない方針。

### server (apps/server)

- Express(REST) + Socket.io(対局のリアルタイム同期)構成。
- 認証は未実装。MVPでは「ゲスト対局トークン」方式にした: 対局作成時にサーバーが`playerToken`をランダム生成してレスポンスで返し、クライアントはsocket接続時にそれを提示して自分の手番(sente/gote)を証明する。Userテーブルとは現状紐付いていない（ログイン機能はまだ無いため）。将来的にログイン機能を作ったら`playerToken`をUserに紐付ける形に拡張する想定。
- CPU戦: `POST /api/games/cpu`でゲーム作成 → socket.io `join`で入室 → 人間が`move`を送るとサーバーがルールエンジンで合法性検証・適用 → CPU番になったら`chooseMove`(反復深化+αβ枝刈りのnegamax、駒得評価、時間予算1.2秒)を自動実行して応手をbroadcast。
- プライベートマッチ: `POST /api/games/private`でルームコード(6桁数字)発行 → 相手が`POST /api/games/private/join`でコード入力して参加。
- 対局中の状態はメモリ上の`Map<gameId, ServerGame>`で保持(揮発性)。指し手と結果はPrismaで`GameMove`/`Game`に永続化するので、サーバー再起動で進行中の対局自体は消えるが履歴は残る設計。**サーバー再起動でも対局を継続できるようにする(メモリ状態の復元)はMVPでは未対応、Phase2以降の課題としてメモしておく。**
- 動作確認: REST + socket.ioの実通信テスト(スクリプトでCPU対局を1手進行)で、人間の着手→サーバー検証→盤面更新→CPU自動応手まで一連の流れが動くことを確認済み。

### web (apps/web)

- `create-next-app`でNext.js 16(App Router) + TypeScript + Tailwindを初期化。自動生成された`.git`は他パッケージと分離運用したくなかったため削除済み（リポジトリ全体としてはまだgit未初期化 — 別途`git init`が必要）。
- ページ構成: `/`(ロビー: CPU戦・プライベートマッチ作成・ルームコード参加) → `/game/[gameId]`(対局画面)。
- セッション管理: 対局作成時に受け取る`playerToken`/`yourColor`を`sessionStorage`に保存し、対局ページでsocket.io接続時に提示する方式（ログイン機能なしのゲスト対局のため）。**タブを閉じる/別ブラウザで開くとセッションが引き継げない点はMVPの既知の制約。**
- 盤面UI: SVGではなくシンプルな9x9のCSS Grid + ボタンで実装（先に動くものを作る優先。将来的にはドラッグ操作や駒アニメーションが欲しくなったらCanvas/SVG化を検討）。後手の駒は`rotate-180`で見分ける。
- 成り(プロモーション)の要否確認は簡易的に`window.confirm`を使用。UIとしては最低限だが、プレースホルダー用のモーダルを作るコストをかけるよりMVPではこれで十分と判断。

### Phase2: ルールセットの拡充

rule-engineに新しいRuleSetプリセットを追加し、サーバー/フロントから選択できるようにした。

1. **駒落ち** (`packages/rule-engine/src/ruleSets/handicap.ts`): 香落ち・角落ち・飛車落ち・飛香落ち・二枚落ち・四枚落ち・六枚落ちを標準ルールセットから該当駒を`without()`ヘルパーで取り除く形で実装。全て標準将棋の伝統的なハンデ設定(公知のルール、著作権問題なし)。

4. **盤サイズ変更(5x5, 3x3)** (`ruleSets/miniBoards.ts`): **法的配慮として、どうぶつしょうぎ等の商標登録された既存の商用ミニ将棋の盤面構成・駒配置は一切参照せず、完全にオリジナルの配置を新規設計した。** 5x5は王・飛・角・銀2枚・歩5枚の構成、3x3は王+金2枚のみの詰将棋風の超ミニ対局。動作確認で「3x3では王同士が隣接できない」という将棋の基本ルールが正しく効いていることも確認できた(ルールエンジンが盤サイズに関わらず正しく汎用動作している証拠)。
5. **自由な初期盤面** (`ruleSets/freeSetup.ts` + `apps/web/app/setup/page.tsx`): スコープを絞り、「自分の陣地(下5段)だけ自由に駒を配置できる。相手(CPU or 対戦相手)は標準配置固定」という形で実装。両陣営が自由配置し合う形は次のステップ。

## 2026-08-31（続き2）: 盤面向き修正・ルール精度向上・Phase3

### 盤面の向き修正

- `apps/web/components/Board.tsx`: 後手視点(`state.yourColor === 'gote'`)のとき、行と列の両方を反転した順序で描画するように変更(`rowOrder`/`colOrder`)。クリックハンドラには常に実座標(row,col)を渡しているので、表示順序を変えるだけでロジック側の変更は不要だった。
- 駒の回転(`rotate-180`)も「後手の駒だから」ではなく「自分の駒でないから」という判定に変更(`cell.owner !== state.yourColor`)。これで先後どちらの視点でも「相手の駒は反転して見える／自分の駒は正立」という一貫した見た目になる。
- **検証で1つハマった点**: 標準将棋の初期配置は先後で180度回転対称なので、反転の有無を初期局面のスクリーンショット比較だけでは判別できなかった(見た目が同じに見えて「反転が効いていないのでは」と誤解しかけた)。実際には1手進めた後の非対称な局面で比較したところ、正しく反転されていることを確認できた。今後同様の見た目検証をする際は、初期局面ではなく非対称な局面で比較するよう注意。

### ルールエンジンの精度向上: 千日手・打ち歩詰め

- **千日手**: `GameState`に局面(盤面+持ち駒+手番)のハッシュ的な文字列キーを持たせ、同一局面が4回出現したら`drawConditions.sennichite`が有効なルールセットでは引き分けにするよう実装(`packages/rule-engine/src/gameState.ts`の`positionKey`)。**連続王手の千日手(本来は反則負けになるべきケース)は区別せず単純な引き分けとして扱う簡易実装**、と明記してある。
- **打ち歩詰め**: 歩を打った結果が相手の即詰みになる手を合法手から除外する処理を`moveGenerator.ts`に追加(`isUchifuzume`)。判定には相手の持ち駒(応手できるかの計算に必要)が要るため、`generateLegalMoves`の引数に`opponentHand`を追加(省略可・デフォルト空オブジェクト)。歩以外の駒(金・銀等)を打って詰ませるのは将棋のルール通り合法のままなことも確認済み。
- 上記2つの実装により、標準将棋および駒落ち・取る一手・5x5/3x3/自由配置の全プリセットで`drawConditions.sennichite: true`に変更(以前はfalseで無効化していた)。
- 呼び出し側(`serialize.ts`, `ai/simpleAi.ts`)も`opponentHand`を渡すように更新。AIのnegamax探索中も打ち歩詰めチェックが効くようになったが、探索は元々時間予算(1.2秒)で打ち切る設計なので、ノード数が多少減るだけで動作自体に問題は出ない(実機で1手あたり約1.6秒、レイテンシ増加なしを確認)。
- 動作確認: Node.jsスクリプトで(1)王同士を往復させて4回目の同一局面で引き分けになること、(2)歩を打つと詰みになる局面でその歩打ちだけが合法手から除外され、同じ局面に金や銀を打つ手は合法手に残ること、をそれぞれ検証済み。

## 2026-08-31（続き3）: ランダムルール条件緩和・両陣営自由配置・連続王手千日手

### ランダムルールマッチングの条件緩和

- `apps/server/src/matchQueue.ts`: ランダムルールマッチングの待機エントリに`RELAX_TIMEOUT_MS`(既定15秒、`MATCH_RELAX_TIMEOUT_MS`環境変数でテスト時に短縮可能にした)後に自動発火するタイマーを持たせ、発火時に「受け入れ範囲を全ルールセットまで緩和」→待機列を再スキャンしてマッチを試みる、という形で実装。
- 即時マッチと緩和後マッチで通知経路がずれる(前者はjoinQueueの戻り値、後者は非同期タイマー)問題は、`node:events`の`EventEmitter`(`matchEvents`)に一本化して解決。`registerMatchSocket`はサーバー起動時に1回しか呼ばれないので、リスナー登録もその中で1回だけ行うようにした(接続ごとに登録すると重複購読になるので要注意ポイントとしてコメントを残した)。

### AIの強化

- 簡易AI(`apps/server/src/ai/simpleAi.ts`)の評価関数に2つ手を入れた:
  1. **獅子・石の駒価値を追加**: `lion: 0`(王と同格。合法手フィルタで実際に取られることはないため0で正しい)、`stone: 1`(それ自体に攻撃力はないが「ただで渡さない」意識づけのため)。
  2. **機動力(モビリティ)項を追加**: 葉ノードの評価に`MOBILITY_WEIGHT(0.15) × (自分の合法手数 - 相手の合法手数)`を加算。特に将棋vs囲碁バリアントのように「駒を打つこと自体が盤面制圧の価値を持つが、駒得計算上は変化しない(持ち駒→盤上に移動しても合計価値は同じ)」ルールでは、駒得評価だけではAIが石を打つ意味を全く理解できない。機動力項を入れることで、石を打って自陣を固める・相手の動きを制限する、といった判断ができるようになった。
- 実装は葉ノード(depth===0)でのみ相手側の合法手数を追加計算する形にし、探索の全ノードで倍のコストがかかることは避けた(自分側の合法手数は元々詰み判定のために計算済みのものを使い回す)。

- レーティング更新: `apps/server/src/rating.ts`に標準的なEloレーティング計算(K=32)を実装。対局終了時、両陣営にuserIdが紐づいている場合のみ更新する(ゲスト同士やゲスト vs ログインユーザーの片方だけの対局は対象外)。
- 動作確認: ログイン済みユーザーがAI初級に投了 → 人間側1500→1484、AI初級側1500→1516に正しく更新されることを確認。人間用/AI用のレーティング一覧(`GET /api/users/leaderboard?type=human|ai`)もプールが分かれて表示されることを確認。

### マッチング相手タイプの選択(人間/AI/どちらでも)

- カジュアルマッチ・ランダムルールマッチングの参加時に`opponentPreference: "human" | "ai" | "either"`を指定できるようにした(`apps/server/src/matchQueue.ts`)。
  - `"ai"`: 待機列を経由せず即座にAI対局を作成(実質CPU戦と同じだが、マッチング画面から選べる)。
  - `"human"`: 従来通り、人間の相手だけを待つ。
  - `"either"`: 人間を優先して探し、条件緩和のタイミング(ランダムルールマッチングは既存のルール緩和と同じタイミング、カジュアルマッチは専用タイマー)で見つからなければAIにフォールバックする。**過疎対策(ユーザーが少なくても必ず対局できる)という当初の目的をさらに一歩進める形になった。**
- AI同士の対局(観戦専用): `POST /api/games/ai-vs-ai`で2つのAIプロファイルを指定して対局を作成。人間のトークンは発行せず、`cpuColors`を両方trueにするだけで、既存の「join時にCPU番なら自動着手をトリガーする」仕組みがそのまま両陣営分機能する(**新しい自動対局ループを書く必要はなく、既存のjoinハンドラの副作用だけで実現できた**)。フロントに`/ai-arena`ページを新設し、先手/後手それぞれのAI強さとルールを選んで観戦を開始できるようにした。
- 動作確認: 別プロセスのスクリプトで`opponentPreference:"either"`のカジュアルマッチに参加し、`MATCH_RELAX_TIMEOUT_MS=2000`のもとで2秒後に自動的にAI対局へフォールバックすることを確認。AI同士の対局も、観戦者が誰もソケット接続していない状態から`join`した瞬間に自動再生が始まり、以降は誰も操作しなくても最後まで進行することを確認。

### AIの強化

- 駒の取り合いの手を優先して探索するMVV-LVA的な並び替え(`moveOrderScore`)を追加。捕獲する駒の価値が高いほど、かつ捕獲に使う駒の価値が低いほど優先度を上げる(価値の高い駒で価値の低い駒を取りに行く筋を後回しにする)、成りの手にも小さいボーナスを加えた。同じ時間予算でもより有望な手を先に調べられるようになり、αβ枝刈りの効率が上がる(実効的な探索深さが伸びる)。
- AIプロファイルを4段階(初級〜最強、depth2〜8・思考時間300ms〜6秒)に拡張し、ロビー・CPU戦・AI同士対局のすべてから選べるようにした。
- **正直な制約**: 開放的な定跡データベースや詰将棋ルーチン、置換表(トランスポジションテーブル)は未実装。今回の強化は「評価関数の改善(前回セッションで実施)+手の並び替え改善+探索時間の選択肢拡大」に留まる。本格的な強豪AIを目指すなら、この先は置換表・null move pruning・詰み探索の専用ルーチンあたりが次の壁になる。

### 棋譜振り返り(評価値グラフ・推奨手)

- `apps/server/src/analysis.ts`: 対局の指し手履歴を最初から`GameState`で再生しながら、各局面でAI(`analyzePosition`、既存のnegamax探索を評価値も返すように拡張した`search`関数の薄いラッパー)に評価値と推奨手を出させる`analyzeGameHistory()`を実装。評価値は常に先手視点に正規化(将棋ソフトの評価値グラフと同じ見方)。手数が多い対局で重くなりすぎないよう、1局面あたりdepth2・300msに制限し、解析対象の手数にも上限(既定80手)を設けている。
- サーバー: `GET /api/games/:gameId/analysis`で対局(進行中・終局後問わず)の解析結果を返す。動作確認で12手の対局が約3.4秒で解析できることを確認(1手あたり約280ms、time budgetの設定通り)。
- フロント: `/game/[gameId]/review`ページを新設。インラインSVGで評価値の推移を折れ線グラフ表示(先手有利=上、後手有利=下)し、AIの推奨手と実際の指し手が異なった手を赤い点でハイライト。手ごとの一覧テーブル(実際の手/推奨手/評価値)も表示する。対局画面から「対局を振り返る」リンクで遷移できる。
- 動作確認: ブラウザで実際にCPU戦を投了まで進め、振り返りページでグラフと推奨手一覧が表示されることを確認。
