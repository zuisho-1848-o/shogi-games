# AI強化ロードマップ

サーバー内蔵AI(`apps/server/src/ai/`)の強化計画。段階を分けて、各段階で実際に指し手の質が上がることを対局で確認しながら進める。

## 🎯 2026-09-01: 最終目標の見直し(2トラック戦略)

ユーザーから「最終的に水匠5・やねうら王・ぴよ将棋クラスの強さにしたい」という要望があり、現在のアプローチ(TypeScript自前実装 + ローカルMac1台での自己対局チューニング)でそこに到達できるか検討した。

**結論: 自前エンジンの延長線上では届かない。** 水匠5・やねうら王は最適化されたC++・ビットボード実装、数百万パラメータのNNUE評価関数、数十億局面規模の学習データ、10年以上の探索技術の蓄積(世界コンピュータ将棋選手権での競争)を背景にしたレーティング4000超級のエンジンで、そもそも比較対象のスケールが違う。ローカルMac1台のTypeScript実装でそこを目指すのは非現実的と判断した。

**そこで方針を2トラックに分けることでユーザーと合意した:**

- **トラックA(自前エンジン)**: 以下Stage 0〜5に従って引き続き強化するが、**目標値を現実的な水準(アマチュア強豪〜将棋ウォーズ二段程度)に修正する。** このエンジンの本当の価値は「変則ルール(獅子王・将棋vs囲碁・自由配置・特殊盤面・取る一手等)に対応できること」にあり、水匠5等は標準ルールしか指せないため、ここは自前エンジンにしかできない領域として引き続き投資する。
- **トラックB(外部エンジン統合)**: 「とにかく最強のAIと対局したい」というニーズには、**やねうら王をUSIプロトコル経由の外部エンジンとして統合する**方針とした(標準ルールのみ対応)。別プロセスとして起動しSTDIN/STDOUT通信する形式(chess.comがStockfishを使うのと同じパターン)。
  - **ライセンス上の注意**: やねうら王本体はGPLv3。別プロセス+プロトコル通信であれば「リンク」に該当せず配布義務は生じない、というのが一般的な解釈だが、法的な最終判断ではない。評価関数ファイル(水匠5等)は作者ごとに個別のライセンス条件があり、**商用サービス(Highstoの実サービス)で使う前に必ず個別に利用規約を確認すること**。これは未確認のまま進めていない。
  - 実装状況: 本セッションでは方針決定のみ。実装は次のステップ。

## Stage 0(実装済み・前回までのセッション)

- 反復深化 + αβ枝刈りのnegamax
- 評価関数: 駒得(`PIECE_VALUES`) + 機動力(自分と相手の合法手数の差)
- 手の並び替え: MVV-LVA的な優先度(取れる駒の価値が高いほど優先)
- AIプロファイル4段階(初級〜最強、depth2〜8・思考時間300ms〜6秒)、それぞれ独立したレーティングを持つ

## Stage 1(本セッションで実装)

**目的: 同じ探索時間でより深く・より正確に読めるようにする。**

1. **置換表(トランスポジションテーブル)**: 局面ハッシュをキーに、既に調べた局面の評価値・最善手をキャッシュする。異なる手順で同じ局面に到達した際に再探索を省略できる(将棋は特に「手順前後」が起きやすいので効果が大きい)。反復深化のイテレーションをまたいで使い回すことで、次の深さの探索の初手候補(最善手)としても活用する。
2. **静止探索(quiescence search)**: 葉ノードでいきなり評価値を確定させると、「次の手で駒が取られる/取れる」ような不安定な局面を過大/過小評価してしまう(地平線効果)。取り合いが続く限り読みを延長し、局面が落ち着いてから評価する。
3. **簡易詰み探索**: 王手の手だけを辿る探索により、数手先までの強制詰みを通常探索より高速に発見する。終盤の即詰みを逃さない/余計な王手を回避する精度が上がる。

## Stage 2(次の段階・未着手)

- **玉の安全度評価**: 玉周辺のマスが相手にどれだけ利いているか、囲いの駒の枚数などを評価関数に加える。現状の駒得+機動力だけでは「玉が薄い」形を正しく避けられない。
- **時間配分の改善**: 全ての手に均等に時間を使うのではなく、候補手同士の評価値が僅差の局面(=難しい局面)によりAI思考時間を配分する。
- **定跡(オープニングブック)**: 序盤は探索よりも定跡データの方が質が高い。人間の棋譜や自己対局から頻出の初手・数手を集めた小さな定跡集を持たせる。

## Stage 3(自己対局によるデータ収集・未着手)

- 既存のAI同士対局機能(`/ai-vs-ai`)を使って大量に自己対局させ、対局ログ(局面・指し手・結果)を蓄積する。
- 蓄積したデータは Stage 4 の学習データにも、後述の詰将棋自動生成の元データにもなる。
- このPC(ローカル1台)でどの程度の局数を現実的な時間で回せるか、まず小規模に試して所要時間を見積もる。

## Stage 4(評価関数の学習・未着手 / 実現可能性を検討済み)

**方針: 本格的なNNUE(数百万パラメータ、数十億局面で学習)やAlphaZero級のMCTS+深層学習は、このPC(ローカルMac、GPU無し想定)では現実的に不可能。段階を踏んで身の丈に合った規模から始める。**

1. **まず線形評価の自動チューニング(Texel tuning的手法)**: 現状手作業で決めている`PIECE_VALUES`や`MOBILITY_WEIGHT`を、自己対局の結果(勝敗)に対してロジスティック回帰的に自動調整する。計算コストが低く、Node.js単体で完結できる。評価関数の構造はそのままなので実装リスクも低い。ここが最初の現実的な一歩。
2. **小型NNUE風ネットワーク**: 上記チューニングで頭打ちになったら、駒の位置関係を特徴量にした小規模な全結合ネット(数百〜数千パラメータ程度)を検討する。学習はNode.js(素朴なSGD実装 or TensorFlow.jsのCPUバックエンド)で完結させる想定。本家NNUEのような差分計算(efficiently updatable)による高速化は将来課題とし、まずは「小さくても学習された評価関数」を動かすことを優先する。
3. **強化学習(自己対局によるTD学習等)**: 教師あり学習(自己対局の結果を教師信号にする)がある程度機能したら、TD(λ)のような手法で継続的に自己改善させることを検討する。AlphaZero的な方策+価値ネットワーク+MCTSは計算資源的に対象外とし、既存のαβ探索+学習済み評価関数、という現実的な組み合わせに留める。

## Stage 5(検討のみ・実装予定なし)

- AlphaZero風のMCTS+深層学習: GPU等の計算資源が前提になるため、クラウドでの学習環境を別途用意しない限りこのPCでは非現実的。将来的に必要になれば改めて検討する。

## トラックB: 外部最強エンジン統合(やねうら王、2026-09-01実装)

「AI最強」ティアで標準ルールに限り本物の強豪エンジンと対局できるようにする。自前エンジン(トラックA)とは別軸の機能として追加した。

### 実装したもの

1. **`apps/server/src/ai/usiEngine.ts`**: `child_process.spawn`でエンジンバイナリを起動し、USIプロトコル(`usi`→`usiok`、`isready`→`readyok`、`position sfen ...`→`go byoyomi ...`→`bestmove ...`)を話す薄いラッパー。`UsiEngine.start()`でハンドシェイク、`goSfen(sfen, {byoyomiMs})`で1手思考させる。
2. **`apps/server/src/ai/sfen.ts`**: 自前`Board`/`Hands`⇄SFEN相互変換。**標準将棋(9x9・標準駒)専用**。内部座標(row0=後手最奥,col0=1筋側)とSFEN(段=row+1、筋=9-col)の対応を実装し、初期局面が公式のSFEN初期値と完全一致することをテストで確認済み。
3. **`apps/server/src/ai/chooseMoveForProfile.ts`**: `AiProfile.engineType`が`"usi"`ならUSIエンジン経由、それ以外(デフォルト)は従来の`simpleAi.ts`を使うよう分岐する非同期ディスパッチャ。標準ルール以外でUSIプロファイルを使おうとした場合はエラーを投げる(SFEN変換が標準将棋前提のため)。エンジンプロセスはパスごとに1つ常駐させて使い回す(`Map<enginePath, UsiEngine>`)。
4. **`apps/server/src/aiProfiles.ts`**: 環境変数`YANEURAOU_ENGINE_PATH`が設定されている場合のみ、`ai_yaneuraou`プロファイル(`engineType:"usi"`)を`AI_PROFILES`に追加する。未設定の環境(デフォルト)では何も変わらず、既存の内蔵AIのみで動作する。
5. `selfPlay.ts` / `socket/gameSocket.ts`のCPU着手箇所を`chooseMoveForProfile`(非同期)に置き換え済み。

### 動作確認

- やねうら王本体([github.com/yaneurao/YaneuraOu](https://github.com/yaneurao/YaneuraOu)、GPLv3)を`vendor/YaneuraOu`にソースからclone・ローカルビルド(`YANEURAOU_ENGINE_MATERIAL`エディション=駒得のみの評価関数、NNUE評価ファイル不要・ライセンス上の懸念なし、Apple Silicon向け`APPLEM1`ターゲット)。ビルド済みバイナリを`vendor/bin/yaneuraou-material`に配置(**`vendor/`は`.gitignore`済みで追跡していない。各自の環境でビルドが必要**)。
- このバイナリを`usiEnginePath`に指定して`chooseMoveForProfile`を実機で呼び出し、標準将棋の初期局面から実際に指し手(`7g7f`相当)が返ってくることを確認した。SFEN変換・USIプロセス通信・指し手のパース、一連の経路が正しく動くことを実証済み。

### 残課題・注意点

- **今動いているのは駒得のみの評価関数(MaterialLv1)であり、水匠5/やねうら王NNUE版のような強さではない。** 「本当に強い」やねうら王にするには、NNUE評価関数ファイル(例: 水匠5同梱のもの)を別途入手して`EvalDir`に配置する必要があるが、**評価関数ファイルは作者ごとに個別のライセンス条件があり、商用サービス(Highstoの実サービス)で使う前に必ず利用規約を個別確認すること。ここは今回も未確認のまま進めていない。**
- 本番(ConoHa VPS、恐らくx86_64 Linux)向けには`TARGET_CPU`(AVX2等)を変えて別途ビルドし直す必要がある。Apple Silicon向けにビルドした`vendor/bin/yaneuraou-material`はmacOS専用。
- `ai_yaneuraou`プロファイルは`YANEURAOU_ENGINE_PATH`環境変数を設定した場合のみ有効になる(`.env`に追記する運用を想定)。現時点でこの変数はデフォルトでは設定していないため、通常運用では従来通り内蔵AIのみが動く。
- 応答速度: `byoyomiMs`は`profile.timeBudgetMs`をそのまま使っている(現状2秒目安)。Webソケット越しの体感速度は未検証(観戦者接続からCPU着手までの実地テストは今回未実施)。

## トラックB「Stage A」: やねうら王の評価関数を駒得のみ→レベル9に強化(2026-09-04実装)

### 背景

自己対局データを増やしても内蔵AI(トラックA)の強さには構造的な上限がある(評価関数が16パラメータの線形結合、探索もTypeScript実装で浅い)ことをユーザーと確認した上で、「このPCで回せる範囲でそこそこ強いものを作るなら、どういうアーキテクチャが良いか」を検討した結果、**探索エンジンは自前で書かず、既に統合済みのやねうら王(GPL、探索部は成熟済み)をそのまま使い、評価関数だけ強化する**方針で合意。3段階(A: 手作り評価関数の強化 / B: 自前学習NNUE / C: 継続的強化学習)のうち、まずAに着手した。

### 実装したこと

やねうら王の`YANEURAOU_ENGINE_MATERIAL`エディションには、作者自身のブログ連載「評価関数を作ってみよう」(http://yaneuraou.yaneu.com/) に対応した**MATERIAL_LEVEL 1〜9の実装が既にソースに同梱されていた**(`vendor/YaneuraOu/source/eval/material/evaluate_material.cpp`)。レベルが上がるごとに次のような評価要素が段階的に追加されていく設計で、コメントに公式ベンチマークでのおおよそのEloゲイン(相対値)も書かれている:

- Lv.2: 盤上の駒の価値を少し減点(手駒との差別化) 
- Lv.3〜4: 駒の利き(利いているマス数)の評価、王からの距離による重み付け
- Lv.5〜7: 利きの評価の精緻化・味方/敵の利きの扱い
- **Lv.8: 玉の8近傍の守り(利き・駒の有無)を評価する簡易的な囲い評価**
- Lv.9: 利きの評価を方向ごとに重み付け

これは自前でPST(piece-square table)や玉の安全度評価をゼロから書く代わりに使える、**既製の・作者自身がテスト済みの・段階的な評価関数強化**だったため、Makefileの`MATERIAL_LEVEL`定数を`1`→`9`に変更してビルドし直すだけで済んだ(コード変更ゼロ)。

### 動作確認

- `make clean && make normal`でMATERIAL_LEVEL=9でのリビルドに成功。`vendor/bin/yaneuraou-material`を更新。
- `chooseMoveForProfile`経由の実機テストで、`byoyomiMs`分(2000ms)実際に思考してから正しい指し手を返すことを確認(レベル1の時と挙動が変わっていることを、応答時間が長くなったことで確認)。

### 強さの検証(2026-09-04実施)

`apps/server/src/scripts/benchmarkEngines.ts`(新設)で、レベル1バイナリとレベル9バイナリを直接対局させて検証した。思考時間を変えて複数回実施した結果、**思考時間の長さによって結果が大きく変わる**という重要な知見が得られた。

| 思考時間(1手あたり) | 対局数 | レベル9の勝敗 |
|---|---|---|
| 0.5秒 | 2局 | 0勝2敗 |
| 1秒 | 20局 | 11勝9敗(ほぼ互角) |
| 3秒 | 8局(打ち切り) | 6勝2敗(75%) |

**結論**: 短い持ち時間ではレベル9の優位性はほぼ消え、むしろ互角〜やや不利になる。思考時間を伸ばすと明確に優位になる(3秒思考で75%勝率)。これは、レベル9の評価関数(利き・玉の囲い評価等)は計算コストが高く、短時間だとその分読める深さが浅くなり、精度向上分を相殺してしまうため と考えられる。**つまり「レベル9への変更は無条件に強くなるわけではなく、実際の対局で使う持ち時間次第」**という点に注意が必要。CPU対戦のAIプロファイルとして採用する場合は、byoyomi(思考時間)を短くしすぎないことが重要になる。

(3秒×16局のテストは8局時点でCPU負荷・ファン音が大きくなったため、傾向が明確に見えた時点でユーザーの判断で打ち切った。)

### 残課題

- 本番(Linux)向けの再ビルドはまだ行っていない(macOS向けのみ)。
- 上記の検証結果を踏まえ、`ai_yaneuraou`プロファイルの`YANEURAOU_BYOYOMI_MS`は短すぎない値(2〜3秒以上)に設定することを推奨する。

## トラックB「Stage B」: 自前学習NNUE評価関数(2026-09-04着手)

### 方針

探索エンジンは引き続きやねうら王(GPL)をそのまま使い、評価関数をNNUE(ニューラルネット)に置き換える。
既存のNNUE評価ファイル(水匠5等)はライセンス未確認のため使えなかったが、**自分で学習させた重みなら
ライセンス問題が根本的に発生しない**。アーキテクチャは最小構成の`halfkp_512x2-16-32`(HalfKP特徴量→512×2→16→32→1)を選択(パラメータ数が少なく学習・検証がしやすいため)。

### 実装したこと(基盤部分)

やねうら王のNNUEファイル形式は完全にドキュメント化されているわけではないため、ソースコード
(`vendor/YaneuraOu/source/eval/nnue/`)を直接読んでバイナリ形式・特徴量エンコーディングを解析した。

1. **特徴量エンコーディング(`ai-training/nnue_format.py`)**: 将棋AI業界で標準的なBonaPiece形式
   (Bonanza/Apery由来、`evaluate.h`のBonaPiece enumをそのまま転記)を実装。盤面座標の変換式
   (`yaneura_square = col*9+row`)、後手視点での180度回転(`inv_square`)、玉を除く全38駒(盤上+持ち駒)の
   特徴量index生成関数を実装し、標準初期局面で先手・後手それぞれ重複のない38個のindexが正しい範囲内で
   生成されることをテストで確認した。
2. **バイナリ書き出し(`ai-training/export_nnue.py`)**: ヘッダ形式・各層(FeatureTransformer/AffineTransform)の
   量子化形式(int16/int8/int32)とパディング・重みの並び順(このビルドではSIMD命令の都合で重みの
   スクランブルが不要と判明)を実装。特に**FeatureTransformer層の重みは通常のnn.Linear層とは転置された
   レイアウト(feature-major)になっている**という、ソースコードを読まないと分からない罠を発見・対応した。
3. **実機での往復検証**: `YANEURAOU_ENGINE_NNUE_HALFKP_512X2_16_32`エディションでやねうら王を別途ビルド
   (`vendor/bin-nnue/yaneuraou-nnue`)。全結合をゼロ初期化したダミーの`nn.bin`を書き出し、実際にこのバイナリが
   **クラッシュせず読み込み、指し手を返す**ことを確認した(ファイルサイズ・レイヤー構造が完全に一致していないと
   ここで失敗するため、フォーマット理解が正しいことの実証になっている)。
4. PyTorch環境をセットアップ(`ai-training/venv`、Apple SiliconのGPU=MPSバックエンドが使えることを確認済み)。

### 学習パイプラインの実装と初回学習(2026-09-04)

上記の基盤(フォーマット・特徴量エンコード)の上に、実際に学習まで一通り動かした。

途中、ELEMENT_WISE_MULTIPLYという特殊な活性化関数の分岐があるように見えて設計を疑う場面があったが、
実際にはSFNNwoPSQT(未使用の別アーキテクチャ)専用の分岐で、今回のhalfkp_512x2-16-32では通常の
「クリップ付きReLU(0〜127にクランプ)」であることをC++側に一時的なデバッグ出力を仕込んで実測し確認した
(ソースの読み違いだったが、勘で進めず実測で確認したことで自信を持って先に進めた)。

1. **学習データエクスポート(`apps/server/src/scripts/exportNnueTrainingData.ts`)**: 自己対局DBから
   標準ルール(`category==="standard"`。HalfKPは標準盤面専用のため)の対局のみを対象に、1局あたり最大10局面を
   サンプリングしてJSONLに出力。`npm run nnue:export-data -w apps/server`で実行(880局から8,778局面を出力)。
2. **学習(`ai-training/train.py`)**: PyTorchで`nn.EmbeddingBag(mode="sum")`を特徴変換層として実装
   (HalfKPのスパースな特徴量→512次元への変換に自然に対応する)。教師信号は既存のTexelチューニング
   (`tuning.ts`)と同じ「対局結果(勝敗)をsigmoidで確率化」方式。Apple SiliconのGPU(MPS)で学習。
3. **量子化書き出し**: C++側の量子化仕様(affine層は固定で2^6倍・特徴変換層はクリップ範囲[0,127]に
   学習時点から合わせてあるので追加スケーリング不要)に合わせた固定スケール量子化を実装
   (動的スケール正規化だとC++側の固定シフト量とズレて壊れることに気づき、修正した)。
4. **実機での動作確認**: 8,778局面・15エポックの学習で訓練誤差(MSE)は0.225→0.063まで低下(学習が実際に
   進んでいることを確認)。書き出した重みを実機のやねうら王NNUE版に読み込ませ、局面によって異なる指し手を
   返すこと(全ゼロ重みの時と違い、意味のある差別化ができていること)を確認した。
5. **強さの検証**: `benchmarkEngines.ts`でMATERIAL_LEVEL9と対局させたところ **0勝10敗**、しかもほぼ全局が
   数手〜十数手で終わる短時間の完敗だった。これは想定内: 特徴変換層だけで約6,400万パラメータあるのに対し
   学習データはわずか8,778局面しかなく、大幅な過学習(訓練データを覚えただけで汎化していない)状態と考えられる。

### 教師あり蒸留への切り替えと、量子化の重大バグ修正(2026-09-04つづき)

- **教師信号を「対局結果」→「やねうら王自身の探索評価値」に変更**: `apps/server/src/ai/usiEngine.ts`に
  `evalSfen()`(info行のscore cp/mateを継続的に記録)を追加、`apps/server/src/scripts/exportNnueTeacherData.ts`
  を新設。CPU負荷を抑えるため教師エンジンは`Threads=1`で動かした(ユーザーからファン音を抑えたいという要望あり、
  246%→96%CPUまで低減。時間はかかるが低負荷を優先)。890局から17,765局面を生成(所要約30分)。
  この方式でのMSEは0.171→0.009まで低下(勝敗方式の0.225→0.063より大幅に改善)。
- **重大バグ発見・修正: 量子化で評価値が常に0になっていた**: 学習後、実機での対局が2回とも0勝10敗
  だったため、量子化済みネットワークが実際に返す評価値を局面ごとに確認したところ、**盤面によらず常に0**
  になっていることが判明。原因は特徴変換層の学習済み重みが小さすぎ(絶対値平均0.01程度)、量子化時に
  整数へ丸めると全部0になっていたため。修正として、学習のforward()内でaccumulatorに固定倍率
  (`FT_ACTIVATION_SCALE=400`)を掛けてからclamp(0,127)するよう変更し(=quantization-aware trainingの簡易版)、
  書き出し時も同じ倍率を掛けてから丸めるようにした。修正後、局面ごとに意味のある評価値を返すようになり、
  評価値の差が大きい局面では符号(有利/不利)がほぼ正しく一致することを確認した。

### 現状の強さ(2026-09-04時点)

上記のバグ修正後も、MATERIAL_LEVEL9との対局は**0勝10敗**(引き続き)。ただし原因は特徴変換層だけで
約6,400万パラメータあるのに対し学習データが17,765局面しかない、明確な**データ不足**だと考えられる
(符号が大きく外れている形跡は無く、僅差の局面でのみ精度が粗い)。ユーザーの合意のもと、
**自己対局デーモンでデータを継続的に貯める方針でしばらく様子を見ることにした**。

### 残課題(次にやること)

- **データ量を大幅に増やす(進行中)**: 自己対局デーモンを継続稼働させ、標準ルールの対局数を増やしてから
  再学習する。目安として現状(890局・17,765局面)の最低でも一桁は増やしたい。
- **量子化を考慮した学習**: 現状は`FT_ACTIVATION_SCALE`による簡易対応のみ。丸め誤差そのものを損失関数に
  織り込む厳密なquantization-aware trainingは未着手。
- **検証用の分割**: 現状は訓練データのみで学習・評価しており、過学習を定量的に検出できていない
  (train/validation分割を導入すべき)。
- **繰り返し学習**: 自己対局デーモン→学習→対局データに反映、のループを継続的に回す仕組み(トラックB
  Stage C「継続的強化学習」に相当)は未着手。
- データが増えてきたら、`npm run nnue:export-teacher-data -w apps/server -- <path> [maxGames] [samplesPerGame] [byoyomiMs]`
  で教師データを再生成し、`python train.py data/teacher_positions.jsonl data/trained_nn.bin <epochs> --teacher`
  で再学習、`benchmarkEngines.ts`で強さを再検証する、という一連の流れを繰り返す。

## 関連機能: 詰将棋の自動生成・出題(2026-09-01実装)

ユーザーからの要望: 「完全なランダムではなく、なるべく実戦で起きやすいケースを詰将棋として出題したい。AI自己対局で複数回出現したケースの活用も検討」。

### 想定アプローチ

1. **自己対局からの抽出**: Stage 3のAI自己対局ログから、詰みで終わった対局を対象に、詰み局面から数手遡った局面を候補にする。
2. **強制詰みの検証**: Stage 1で実装する簡易詰み探索エンジンを使い、候補局面から本当に(受け方の応手に関わらず)詰むかを検証する。詰み手数(1手・3手・5手…)を難易度の目安にする。
3. **頻出パターンの重み付け**: 同じ(または類似の)詰みパターンが自己対局で複数回出現した場合、それを「実戦で起きやすい典型的な詰み筋」として優先的に採用する。局面の類似判定は、駒の相対配置(玉の周りの駒構成など)でクラスタリングする方式を想定。
4. **データモデル**: `Puzzle`テーブル(仮)に局面(RuleSet設定+盤面)・解答手順・詰み手数・出典対局ID・出現回数を保存。
5. **出題UI**: 局面を表示し、ユーザーが指し手を入力→サーバー側で「その後も強制詰みが継続するか」を都度再検証する(想定解と完全一致でなくても、別の正解手順を許容できるように)。

### 実装したもの(2026-09-01)

Stage1(詰み探索エンジン`findForcedMate`)とStage3(自己対局データ)がある程度揃った段階で実装した。

- **Prisma `Puzzle`モデル**: 出題局面(盤面・持ち駒・攻め方をJSONで保存)、検証済み解答手順、詰み手数、出典対局ID、同種パターンの出現回数。
- **`apps/server/src/puzzles.ts`**:
  - `generatePuzzlesFromSelfPlayGames()`: AI自己対局(`isSenteCpu&&isGoteCpu`)かつ`resultStatus:"checkmate"`の対局を対象に、終局から遡って`findForcedMate`で強制詰みを検証できる局面を抽出する。**実際にその対局で指された手順ではなく、findForcedMateで検証し直した手順を解答として保存する**ことで、相手の受けが実戦では最善でなかった場合でも解答の正しさを保証している(設計時に決めた「強制詰みの検証」方針通り)。
  - 重複排除: 玉の周囲9マスの駒配置+攻め方の持ち駒を正規化したシグネチャで同種パターンを判定し、重複は`occurrenceCount`をインクリメントするだけに留める(「頻出パターンの重み付け」に相当)。
  - `attemptPuzzleMove()`: ユーザーの一手を`generateLegalMoves`で合法性検証 → 適用 → 詰みなら正解終了、そうでなければ`findForcedMate`で「まだ強制詰みが継続するか」を再検証する。**元の想定手順と一致しなくても、別の正解手順を許容する**設計(想定通り)。受け方の応手はサーバー側が自動で指す(合法手はすべて詰みに至る性質を利用し、最初に見つかった手を採用)。
  - 実装中に発見・修正したバグ: 玉が盤端にいる局面(詰みでは非常によくある)で重複判定用の周囲9マス走査が盤外座標にアクセスして例外を投げていた(`Board.inBounds`チェック漏れ)。
- **CLI**: `npm run puzzles:generate -w apps/server`。実データ(自己対局99局)から8問生成できることを確認。
- **API**: `GET /api/puzzles`(一覧)、`GET /api/puzzles/:id`(詳細)、`POST /api/puzzles/:id/attempt`(一手提出・検証)。
- **Web UI**: `/puzzles`(一覧)、`/puzzles/[puzzleId]`(出題・解答)。盤面クリック→候補手をサーバーに送信→合法性・詰み継続を検証、という一連をブラウザで実地確認済み(1手詰め問題を実際に解いて「詰みです。正解！」が表示されることを確認)。

### 動作確認で分かったこと

- サーバー側の「別解も許容する」ロジックが実際に機能していることを確認した: あるテストで、サーバーが選んだ受け方の応手(玉の逃げ場所)が保存済み解答手順とは異なる手だったにもかかわらず、続く攻め方の手で正しく詰みが成立した。
- 攻め方の手をクライアント側では合法手フィルタしていない(盤面クリックをそのまま送る設計)ため、サーバー側で`generateLegalMoves`による検証を追加で入れた(存在しない駒を動かそうとする等の不正な手を弾けることを確認済み)。
